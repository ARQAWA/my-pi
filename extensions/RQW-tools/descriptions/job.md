Wait for, check or kill your background jobs. A bash, codemode, read, edit, write, grep or find call still running after 12 seconds returns a job id (job#N) and keeps running. Later calls of the same response still run after it, as queued jobs. Calls of your later responses wait for a bash job only where they change what its result lists under `holds:` (the package folder an install changes, the git index, the exact files it writes); otherwise they do not wait, so wait for it before anything that needs its result. A read, edit or write of a file that changed while a job runs gets a note. When a bash or codemode job ends, its result has an `effects` report of the files changed while it ran (who changed them, your own edits, deleted files; an incomplete scan says why under `errors`); a job that ends unseen with such a report adds one note line to your next tool result.
- wait: returns as soon as one of `ids` ends (with any other that ends within a quarter second), with their full results, or at `timeout_ms` with the status of each; jobs keep running after a timeout. With `until` (a regular expression) it also returns as soon as a job's output matches it, with the matching line, while the job keeps running: use it to wait for a server to be ready. Estimate how long the job still needs and set `timeout_ms` somewhat longer; 300000 is only the default when omitted. Waiting costs no tokens; do not poll status instead of waiting.
- status: state, exit code, elapsed time, the last `lines` lines of output (default 20) and the log file of each job in `ids`, or of all your jobs without `ids`. Read the log file with read or grep for more.
- kill: stops a job and all its child processes, or cancels a queued one. Queued calls of the same response that wait for it are cancelled too and listed in `cancelled_followers`.
Wait for or kill your jobs before your final answer, unless the user wants them left running.
