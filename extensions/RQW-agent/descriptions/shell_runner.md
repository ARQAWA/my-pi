Run a shell_runner: a cheap worker session that runs the commands you give it and reports the outcome. Use it for noisy mechanical work (builds, test suites, installs, service starts, long logs, read-only git) that burns tokens; do not use it when the brief would be longer than running the command yourself. One assignment per start; each start uses a fresh context, so the brief must be complete. Trust the result: per command it returns the exit code, duration, a one-line outcome, the verbatim error lines and the path of the full output. Independent calls may run in parallel. Omit action (or use start) with task to start a fresh assignment. send (id, task) explicitly continues the same assignment/history; interrupt preserves history, stop releases it, restart (id, optional task) starts fresh. Completed sessions remain until stop. Role, model and tools cannot be overridden. By default children inherit GPT Fast; pass fast_gpt false when the user forbids Fast for subagents. Work in parallel while children run. When blocked, estimate how long their remaining work should take and set timeout_ms somewhat longer on each action=wait call; 300000 is only the omitted default, not a required interval or maximum. wait takes full ids (may mix any of your direct children) and mechanically returns the first result without model turns while waiting. Timeout returns compact status only; children keep running and you may re-estimate and wait again. Use action=status (ids, messages: 5-10, default 8) for the last trimmed messages and in-flight tool calls; decide whether to wait, send, interrupt, stop or restart. Do not busy-poll. Results arrive once: through wait or a later [shell_runner#N] message; already-delivered results give a receipt. For start, task is the brief, with these fields: directory; commands in order; timeout; on failure stop or continue. The worker chooses no other commands, fixes nothing and changes no git state. start returns shell_runner#N at once.
