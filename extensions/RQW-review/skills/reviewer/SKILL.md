# Reviewer

Blind review by a separate read-only model that works with you as one team for the user's agreement: it checks the requested criterion, including checks beyond the agreement and exclusions, and gets the user's own messages verbatim. Use it when the user asks for a review or a checked result: his skills `$blindreview` and `$highreview` ask for these levels, and a skill he calls may run it as its procedure. Launch a reviewer when the user, the caller's brief, an invoked skill or applicable project instructions require it. Without such a request or requirement, never launch one on your own initiative or as an automatic step of other work. Keep working meanwhile, but leave the reviewed files unchanged until its verdict.

- Level: blind by default; high when the user asks for it. The level picks the profile: blind `spotty` (`gpt-6.1-terra` medium), high `bossy` (`gpt-6.1-terra` xhigh). Launch a fresh child for the initial review and for each changed-object pass with `agent({action: "start", agent_type: "spotty", role_file: "<absolute RQW-review/REVIEWER.md>", include: ["user_messages"], task: ...})` for blind or `agent({action: "start", agent_type: "bossy", role_file: "<absolute RQW-review/REVIEWER.md>", include: ["user_messages"], task: ...})` for high. Replace the placeholder with the absolute path of the package `REVIEWER.md`, found at `../../REVIEWER.md` from this skill file; `role_file` itself resolves against the caller's cwd, so never pass that relative path. The explicit package role prevents a same-name personal or project profile from replacing the review contract, while the selected profile still supplies its model and effort defaults. The task plus included user messages are the reviewer's input, with every path absolute when the work runs in another directory. The ordinary `agent` tool from RQW-agent is required; if it, the selected profile or the package role file is unavailable, report that the reviewer cannot run. There is no standalone review tool or fallback.
- Brief: put the task sections below in this order; agent mechanically appends `<user_messages>` at the END, after the task. Do not reproduce user messages yourself. Supply primary requirement and governing-rule sources, not only Main's summary; each reviewer reads them independently, including any required user-facing explanation rules:
  - `<agreement>`, only when needed: only decisions the user himself accepted, verbatim, each with its source and evidence of his acceptance. Main's or another agent's approval is not agreement.
  - `<object>`: exact paths or readable references to the object, primary requirements, applicable governing rules and source evidence, the diff as a file path, and the stage: pre-action or pre-completion; use the saved rules for a versioned workflow.
  - `<criterion>`: what this check confirms and which deliverable must fulfill each obligation; an exclusion cannot silently waive a governing requirement of this pass. Always include: "Report an unagreed element only when its concrete effect changes the ordered result, expands scope or adds material risk, subject to the role's severity gate."
  - `<rejected_earlier>`, from a changed-object pass on: the findings rejected in earlier passes, each with its reason.
  - `<user_messages>`: agent appends every message of the user in this conversation, verbatim and in order, after all task sections via `include: ["user_messages"]`; these are raw user texts, not compaction or branch summaries.
- Do not impose file, search, tool-call or turn quotas on a reviewer. Read-only inspection may take as many calls as the in-scope check needs; large or truncated sources are read in complete parts.
- The executor fixes format slips itself without a new pass; this does not replace missing material evidence.
- The verdict comes as the reviewer's final:
  - `CLEAN` with concise concrete `CHECKED:` evidence and no `UNCHECKED:`: this pass passed. Evidence names what was inspected and the exact files, sections or source anchors that establish it; it is not a long per-obligation checklist. Run no extra pass for confidence, but preserve every independent pass required by the invoking procedure.
  - `FINDINGS:`: your teammate's findings. For a review-only task, report the verified findings without changes; the correction loop below applies only when the task authorizes changes. Find each quote by searching for it. Matching quotes are necessary, not sufficient: admit a finding only through the role's severity gate, with a concrete trigger and wrong outcome in the ordered result. Admit P3 only in a pass with an admitted P0-P2 finding, and fix them together; a P3-only pass counts as CLEAN, with its P3 dropped and not mentioned. For an omission, verify the quoted requirement and the complete inspected file/section instead of demanding nonexistent text: fix it exactly to its REQUIRED OUTCOME and no further; do not reject it, argue with it or put it to the user. Reject a finding when it fails the role's severity gate, a quote is not verbatim, the allegedly missing content is present in the cited object, or a NOT AGREED element is covered by a verbatim quote of the agreement, and give that reason with the quote. Fix all admitted findings in one batch, then launch a fresh reviewer at the same level and criterion with the fixes, changed lines, affected paths and every rejection so far in `<rejected_earlier>`. A changed-object pass checks those fixes, lines and paths, not the whole object again. Stop when no admitted finding remains and the required evidence is complete.
  - `UNCHECKED:`, missing required `CHECKED:` evidence, a bare `CLEAN`, or malformed evidence: the check is incomplete regardless of its leading verdict. `send` the SAME reviewer a short request to supply concise concrete evidence from its retained inspection or mark the exact unavailable requirement `UNCHECKED:`. Do not start a fresh reviewer merely for format or evidence completion, and never record an incomplete result as acceptance.
  - No verdict, a provider error or a reviewer that could not start: the check has not passed, and no self-check replaces it. Retry the unchanged failed review once under this bounded failure rule; if it fails again, tell the user and wait. A fresh reviewer is otherwise for a changed object or admitted findings requiring a new pass, never for confidence.

When changing this review contract, validate it against known defective, corrected and missing-source examples before claiming improved detection. These checks are not extra rounds in ordinary task reviews.
